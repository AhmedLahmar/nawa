1 · Executive summary

Nawa today is a front-end-only Angular application. Every "backend" behaviour — accounts, posts, funding, AI, live streaming — is simulated in the browser using an in-memory store persisted to localStorage. This document describes how to turn it into a real, multi-user platform on a startup budget, and sequences the work into six phases so value ships early and the hardest, most expensive, most regulated features come last.

The core decision is to build on Supabase (a managed Postgres backend providing database, authentication, file storage, realtime, and serverless functions) rather than assembling raw cloud primitives. This keeps fixed cost near zero while small, lets a one-to-two person team move fast, and — because Supabase is Postgres underneath — leaves a clean migration path to Azure or any cloud later, once traction justifies it.

All simulated behaviour is replaced with real implementations. The AI idea validator and roadmap generator call OpenAI for genuine, idea-specific analysis from day one — grounded with real market data (web-search sourced), never templated. Money (crowdfunding, marketplace, payouts) is deferred to Phase 5 because it carries both payment-provider constraints in Tunisia and a formal regulatory framework.

Non-negotiable security rule

The OpenAI key (and later the Stripe secret key) must never appear in the Angular bundle. The browser ships to the public, so anything in it is public. All secret-bearing calls go through Supabase Edge Functions: Angular → Edge Function → OpenAI/Stripe.

6 · The phased roadmap

Phases are sequenced so the thesis — founders build in public to earn credibility, then get funded — is validated before any money or heavy infrastructure is built. Each phase ships something usable on its own.

Figure 2 — Six phases. The first three are cheap and fast; cost and risk rise toward the right.

7 · Phase 1 — Credibility core + real AI onboarding MVP

Goal: a real founder signs up, describes their idea, gets a real AI validation and roadmap, creates a startup page, and builds in public with real followers and a real Founder Score. This is the smallest version that is genuinely useful and tests the core thesis.

Scope

  • Authentication (email + social) and user profiles with roles
  • Startup pages: stages, KPIs, journey, team
  • Build-in-public feed: the eight post types, comments, supports, follows
  • Real AI onboarding: idea validator + roadmap generator (see §8)
  • Founder Score computed from real activity
  • Discovery and search

Explicitly out of scope for Phase 1: messaging, live, experts, marketplace, funding — these are hidden or disabled until their phase.

Phase 1 data model (core tables)

Figure 3 — Phase 1 relational model. Rich sub-structures (stages, KPIs, media) stay as JSONB; relationships that need querying (follows, comments) are their own tables.

Authorization via Row-Level Security (RLS)

Instead of a hand-written server, most access rules live in the database as RLS policies. Examples:

  • Anyone can read public profiles, startups, and posts.
  • A user can insert/update/delete a startup only where founder_id = auth.uid().
  • A user can comment or support as themselves only.

Migration plan — swap the mock Store for Supabase

The Angular Store stays as the app's single data access point; its internals change from localStorage arrays to Supabase queries. This is done table by table so the app keeps working throughout:

  1. Create the Supabase project and apply the Phase 1 schema + RLS.
  2. Seed reference data; wire Supabase Auth into the existing onboarding screens.
  3. Replace Store read methods (profiles → startups → posts → follows) with Supabase reads.
  4. Replace write methods (publish, follow, comment, support) with Supabase writes.
  5. Move the Founder Score calculation into an Edge Function triggered on activity.
  6. Remove mock-data.ts and the deterministic ai.ts; delete the admin "reset demo" control.

Phase 1 exit criteria

Real users can register, onboard with real AI analysis, publish updates, follow each other, and see a Founder Score that reflects real activity — with zero simulated data anywhere in the flow.

8 · The AI idea validator — prompt & contract

The validator is the first magical moment of the product, so it ships real in Phase 1. The flow:

Figure 4 — Validator flow. The Edge Function grounds the analysis with sourced data (Option C), then asks the model for a strict JSON result.

Design choices

  • Model: gpt-4o-mini — strong enough for structured analysis, ~16× cheaper than the full model.
  • Output: OpenAI structured outputs (JSON schema mode) forcing a response that maps exactly to the existing IdeaAnalysis type — so it renders in the current UI with no reformatting.
  • Grounding (Option C): the function first fetches real market indicators (search), then passes them to the model, which must cite them. Numbers it cannot ground are labelled as estimates.
  • Persona: a candid MENA-focused startup analyst — specific, willing to push back on weak ideas, quantifying in local currency.

System prompt (draft — to be tuned by the team)

// system
You are a startup analyst for the Tunisian and wider MENA market, embedded in
Nawa, a build-in-public platform. You evaluate a founder's idea with honesty and
specificity. You are supportive but never flattering: if an idea is weak, you say
so and explain why.

Rules:
- Ground every market figure in the SOURCED DATA provided to you. If a number is
  not supported by that data, either omit it or clearly mark it "estimate".
- Quantify in the founder's local currency when known (TND for Tunisia).
- Name a concrete beachhead customer and a concrete next experiment.
- Prefer the realistic competitor (the status quo, a WhatsApp group, an
  intermediary) over naming big foreign startups.
- Never invent statistics, company names, or regulations.
- Return ONLY valid JSON matching the provided schema. No prose outside the JSON.

User prompt template

// user
FOUNDER IDEA:
"""{{idea}}"""

CONTEXT:
- City: {{city}}         - Country: {{country}}
- Stated role: {{role}}

SOURCED DATA (use for all market figures; cite in the notes fields):
{{search_results_json}}

Produce the full idea analysis as JSON matching the schema.

Enforced output schema (maps to IdeaAnalysis)

{
  "name": string,              // suggested startup name
  "tagline": string,
  "industry": enum,           // FinTech | AgriTech | AI | ...
  "emoji": string,
  "opportunityScore": number, // 0-100, justified
  "marketPotential": enum,    // Low | Medium | High
  "competition": enum,
  "risk": enum,
  "timing": string,
  "marketSize": [{ label, value, note }],  // note cites the source
  "competitors": [{ name, note, kind }],
  "strengths": string[],
  "risks": string[],
  "nextStep": string,
  "mvp": [{ label, why }],
  "pricing": string,
  "segments": string[]
}

Why Option C (sourced data) matters here

Founders will screenshot this analysis and show it to investors and incubators. A model left to invent TAM/SAM/SOM produces confident but unfounded numbers. Grounding the figures in real sources — and labelling anything unsourced as an estimate — protects both the founder's and Nawa's credibility.

10 · Phase 3 — The Copilot assistant

Goal: the differentiating "co-founder in your pocket" — ongoing, context-aware Q&A.

Unlike the one-shot validator, the Copilot answers open-ended questions ("why am I not getting customers?") using the founder's real startup state as context: current stage, KPIs, roadmap progress, follower count, campaign status. It runs through the same Edge Function pattern, injecting a compact context summary into each prompt. This is placed after community features because it is the clearest ongoing per-message cost and benefits from having real activity to reason about.

  • Context builder: an Edge Function assembles a short, structured snapshot of the founder's startup.
  • Guardrails: the assistant stays on startup topics and refuses to fabricate numbers about the user's own data.
  • Cost control: short context, small model, optional per-user daily message cap.

12 · Phase 5 — Money regulated

Goal: close the loop with real money — only after traction and legal footing. This is the hardest phase and has two distinct hard parts: a payment provider, and regulation.

Payment provider — Tunisia reality

Stripe is not available to Tunisia-based businesses; Tunisian founders typically only access it via a foreign (e.g. US) entity. For a Tunisia-first platform, plan around a local gateway authorised by the Banque Centrale de Tunisie — e.g. Flouci or Konnect, which accept national bank cards and mobile wallets in TND. Design the payments layer behind an interface so the specific gateway can be swapped per market.

Regulation — crowdfunding is a licensed activity

Tunisia regulates crowdfunding under Law No. 2020-37 (6 August 2020), with application decrees published in October 2022 covering three distinct forms: investment in securities, lending, and donations/gifts. The securities-investment form is overseen by the CMF (financial market council). The practical implication for Nawa:

  • Running a crowdfunding platform that collects money from the public is a regulated activity, not just a payments integration.
  • Which form Nawa operates (rewards/donations vs. equity/lending) determines the licensing path and the regulator involved.
  • This requires legal counsel before launch — it is a business/legal decision, not only an engineering one.

Build order within Phase 5 (increasing complexity)

  1. Marketplace payments — simplest: a buyer pays a seller for a product via the gateway.
  2. Donations / tip jar — direct support, same payment rails.
  3. Community rounds (crowdfunding) — the regulated piece; gated on the legal path above.
  4. Wallet & payouts — paying founders out, which adds KYC/identity obligations.

Recommendation: begin the legal/licensing investigation at the start of the build (it has a long lead time) even though the code lands in Phase 5. Launch marketplace + donations first; open community rounds only once the regulatory path is cleared.

13 · Phase 6 — Live streaming

Goal: the richest, most infrastructure-heavy feature, built last.

Supabase has no video product, so live streaming uses a specialist provider — Mux, LiveKit, or Agora. Live chat and reactions run on Supabase Realtime; live gifts depend on the Phase 5 payment rails. This phase is last because it combines the highest ongoing infrastructure cost with a dependency on payments already being live.

*gpt-4o-mini list price: $0.15 per 1M input tokens, $0.60 per 1M output tokens. A single idea analysis is a few thousand tokens — a fraction of a cent. Supabase Free is $0; Pro starts at $25/org/month plus usage-based overages. Supabase is billed per organisation with included quotas (database, storage, egress, monthly active users).

The design keeps the only recurring per-user cost (AI calls) proportional to usage, and defers all fixed infrastructure cost until a phase genuinely needs it. Phases 1–2 can run at effectively zero fixed cost.
